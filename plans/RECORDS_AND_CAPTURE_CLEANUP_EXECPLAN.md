# Run records in the source tree, one readable RSI capture per session, touch file written by the app, tidy python folder

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log` and `Outcomes & Retrospective` must be kept up to date as work proceeds. It is maintained in accordance with `PLANS.md` at the repository root.

Five rules override `PLANS.md` for this plan. First, the implementing agent never runs a build, CMake configure, QML lint, the application or a test unless the user asks for that run (`AGENTS.md`, "Validation and handoff"); where a milestone names a build or a run, the agent records it as "not run (user's)" in `Progress` and continues. Python analysis scripts on recorded files may be run by the agent (`python -I`, isolated mode, so that no module from the data folders is imported). Second, the agent never moves the robot, never connects to the PLC, RSI or FTS hardware and never starts a KRL program; runs that need the robot are done by the user and need the user's explicit authorization for that run. Third, no git staging, commits, `git rm` or `git mv` unless the user asks; files are created, moved and deleted in the working tree only. Fourth, no project tests or test harnesses. Fifth, every line obeys `AGENTS.md`, in particular "Mandatory C++ style" (no lambdas, no project templates, no thrown exceptions, results through return values, at most four parameters) and "Mandatory code reduction".


## Purpose / Big Picture

Today every file a run produces (RSI packet captures, Sampling plans, calibration results, PLC and force-sensor logs) is written to `records/` beside `robocrap.exe` inside the build folder `build/Felgo_SDK_Desktop_Qt_6_8_3_MinGW_64_bit-Debug/`, so deleting the build folder deletes all measurements. A probe calibration session of 158 touches leaves 158 packet-capture files (`rsi_packets_<id>.csv`, `_part2` … `_part158`), 116 MB of rows whose main column is Base64 text, prints 158 "saved RSI diagnostic" lines to the console, and the joint angles of the touches exist only after running `python/rsi_touches.py`. The `python/` folder mixes unused plotting scripts, a script reading a file that no longer exists and data files at one level.

After this plan: all run files go to `records/` in the repository folder (ignored by git); one session has one packet-capture file with plain columns (IPOC, Start, Touch, joint angles, corrections, timings) that a person can read in a spreadsheet; the console shows nothing from the calibration run except errors; at the end of a calibration run the application writes `calibration_touches_<id>.csv`, one row per detected touch with its six joint angles; `python/` holds `rsi/rsi_packet_timing.py`, `calibration/calibration_fit.py` (an offline copy of the application's calibration fit, used for plan studies) and `forces/forces_analysis.py` with its data, and nothing else.

To see it working: build, run "RSI Sampling" of the calibration path (no robot needed) and observe `records/<id>/rsi_plan_<id>.csv` in the repository folder; after a user-authorized calibration run, observe one `rsi_packets_<id>.csv` and one `calibration_touches_<id>.csv` there and a quiet console; run `python -I python/calibration/calibration_fit.py records/<id>` and see the same numbers as the "Calibration complete" window.

## Surprises & Discoveries

- Observation: the 158 capture files are not intended per touch; they are a side effect of the save timer. `RsiDevice::appendTrace` restarts a 250 ms single-shot timer (`m_traceTimer`) on every row, and `saveTrace` writes a new file (`_part` + `m_tracePart`) whenever the timer fires. Between two searches the controller sends no RSI packets for more than 250 ms, so every search becomes one file, and every saved file prints `[OK] saved RSI diagnostic …` (`saveTrace`, `qInfo` of the finished future).
  Evidence: `src/devices/rsi/rsidevice.cpp`, `startDevice` (interval 250), `appendTrace`, `saveTrace`; session `calibration_20261118_113045_223` has 158 capture files.
- Observation: `python/rsi_packet_timing.py` needs from received packets the IPOC, the `Delay D` attribute and `RIst` X…C, and from replies the stream index, IPOC, Stop/Result and the four handler times; nothing in the repository reads `MACur` (motor currents) or the other XML elements.
  Evidence: `read_packets` in `python/rsi_packet_timing.py`; `git grep MACur` finds it only in documents, plans and the controller configuration `resources/files/rsi/RSI_EthernetConfig.xml` (which makes the controller send it), not in `src/` or `python/`.
- Observation: an empty folder `records/` already exists at the repository root (created 2026-11-18) and is not ignored by git.
- Observation: the first session after Milestone 2 (`calibration_20261118_160007_715`) has more late RSI packets than earlier sessions: 140 received packets with `Delay` > 0 (largest D 6) and 107 requests left unanswered, against 2 and 1 in `calibration_20261118_113045_223` and 7 and 7 in `calibration_20261117_132108_323`; 23 receive gaps between consecutive 4 ms packets exceed 15 ms (largest 29.8 ms), in 17 searches, 0.4–2 s after the search start. For the gaps the reply's thread times show the `ControlIO` thread asleep in its event loop for 16–22 ms before the late packet, entering the handler 0.07–0.43 ms after waking and having finished its previous handler 0.01–0.09 ms before sleeping: the packets reached the PC late; the handler was not busy. Capture saves run 250 ms after a search ends, in a worker thread, and none falls inside a search. Conclusion so far: not caused by the Milestone 2 change; the PC or network delivered the datagrams late (compare the `RSITimeout` of 2026-11-14 in `docs/hardware context/HARDWARE_SETUP.md`). The run completed; RSI `Timeout` = 10 was not reached.
  Evidence: `records/calibration_20261118_160007_715/rsi_packets_calibration_20261118_160007_715.csv`, columns `delay`, `pc_ns`, `entry_ns`, `sleep_ns`, `wake_ns`, `prev_done_ns`.
- Observation (2026-11-18, after session `calibration_20261118_164135_671`): late requests over all nine sessions (rx, unanswered = rx − tx, rx with `Delay` > 0, receive gaps between consecutive 4 ms requests above 8 and 15 ms, largest gap): `20261114_170013_165` 2/3/2/0/10.9 ms; `20261117_113235_576` 8/9/1/1/20.6; `…121258_825` 0/3/0/0/6.7; `…124928_908` 2/4/2/0/11.1; `…130745_826` (18 touches) 146/255/49/25/50.3; `…132108_323` 7/7/2/1/28.8; `…113045_223` 1/2/1/0/11.3; `…160007_715` 107/140/30/23/29.8; `…164135_671` 27/46/6/5/28.8. The late requests already occurred before this plan's code changes (`130745_826`, 17 Nov). After every gap above 15 ms, 4–7 requests arrive within 0.3 ms of each other, about the number of 4 ms cycles in the gap: the requests were held below the application and delivered together. The late touches differ between sessions (touches 34–148 in `160007_715`, 5, 47, 50 in `164135_671`), so robot pose is not the cause. Disk `E:` is SATA, not USB. The RSI adapter (ASIX AX88179, USB) and the Wi-Fi adapter (Realtek 8811CU, USB, carrying the internet and the WireGuard tunnel `AustriaViennaS9`) share the one Intel xHCI host controller. Adapter settings read 2026-11-18: Energy-Efficient Ethernet off, flow control on, Interrupt Moderation Rate Middle, adapter SelectiveSuspend on (SSIdleTimeout 60 s); power plan Balanced, display off and sleep Never, USB selective suspend off. Windows logs show no Defender or system event during the late requests, except that the Claude desktop VM service was reinstalled and restarted at 19:08:15 during `160007_715`. Cause not established; the next measurement must separate arrival at the adapter driver (Npcap/Wireshark is installed and bound to `KRC4-Direct`, or `pktmon`) from delivery to the application, and record driver latency (for example LatencyMon) during a run.

## Context and Orientation

The repository is a Windows Qt Quick application (C++17, Qt 6.8, CMake). The robot is a KUKA KR 10 with a KR C4 controller. RSI (KUKA RobotSensorInterface) is a controller option that, while a KRL program runs a sensor-guided motion, sends the PC one XML packet every 4 ms and accepts a reply with a position correction. KRL is the robot's programming language. A "Sampling" is the application step ("RSI Sampling" toolbar button) that computes a motion as a table of corrections and gives it an identifier `<id>` (for calibration `calibration_<UTC yyyyMMdd_HHmmss_zzz>`), which names the record folder `records/<id>/`. A "touch" is one search motion of the probe toward the calibration sphere, stopped by the controller when the probe signal switches on; one calibration session has 158 touches numbered 1–158.

Writers of `records/` today, each computing `QDir(QCoreApplication::applicationDirPath()).filePath("records")` itself: `RsiDevice::writeTrace` in `src/devices/rsi/rsidevice.cpp` (packet captures); `PlcDevice::openLog` in `src/devices/plc/plcdevice.cpp` (`records/plc_io_<time>.csv`); `FtsDevice::saveLogToDefaultFile` in `src/devices/fts/ftsdevice.cpp` (`records/fts_<time>_<uuid>.json`); the plan writer in `src/trajectories/probe/probersistream.cpp` (`records/<id>/rsi_plan_<id>.csv`, around line 172); the plan writer in `src/trajectories/chamfer/chamferrsistream.cpp` (around line 80); `writeCalibrationResult` in `src/application/scene/scenemachiningpreparation.cpp` (`records/<id>/calibration_result_<id>.csv`). `SceneCalibration` reads `resources/json/calibration_sphere.json` beside the executable; that is a resource, not a record, and does not change.

The packet capture. `RsiDevice` (class in `src/devices/include/devices/rsi/rsidevice.h`) runs on the I/O thread named `ControlIO`. In `onReadyRead` it reads all pending datagrams, decodes each with `decodeRequest`, answers only the newest, and only after the reply appends the rows to the in-memory buffer `m_trace` with `appendTrace`. A received row is `pc_ns,rx,-1,-1,-1,<Base64 of the XML>`; a reply row is `pc_ns,tx,<stream_index>,<write_bytes>,<write_ns>,<Base64 of the reply XML>,<entry_ns>,<sleep_ns>,<wake_ns>,<prev_done_ns>`. `appendTrace` restarts the 250 ms timer `m_traceTimer`; when it fires, `saveTrace` moves the buffer into a `std::async` worker running the static `writeTrace(rows, fileName)`, which writes the file with `QSaveFile` and returns a status string; `saveTrace` prints the strings of finished workers. `setCorrections` (a new table and identifier) and `disconnect` also call `saveTrace`; `stopDevice` waits for all workers. A received request XML looks like (abbreviated):

    <Rob Type="KUKA"><RIst X="1054.143188" Y="-331.970093" Z="467.959290" A="..." B="..." C="..."/>
    <AIPos A1="17.476164" A2="-54.583924" A3="80.662037" A4="0.000058" A5="63.921136" A6="17.476263"/>
    <MACur .../><Delay D="0"/><Start>1</Start><Result>0</Result><TouchIndex>1</TouchIndex>
    <Touch>1</Touch><IPOC>4977706</IPOC></Rob>

and a reply (built by `encodeReply`):

    <Sen Type="ImFree"><RKorr X="0.004000" Y="0.000000" Z="0.000000" A="0.000000" B="0.000000"
    C="0.000000"/><Stop>0</Stop><Result>0</Result><IPOC>4977706</IPOC></Sen>

The calibration run. `SceneMachiningPreparation` (`src/application/scene/scenemachiningpreparation.*`, GUI thread) starts program 1 through the PLC in `startCalibration`, collects `ProbeTouchDetection{touch, joints}` in `m_detections` from the queued signal `RsiDevice::touchDetected` (slot `recordTouch`), and in `endRun(error)` computes `fitProbeCalibration` (`src/trajectories/probe/probecalibrationfit.cpp`), fills the result window rows and calls `writeCalibrationResult(fit, id)`. The held job `m_preparedCalibration` carries `diagnosticId`.

Python. `python/rsi_touches.py` reads all capture files of a session and writes `rsi_touches_<id>.csv` (per touch the first packet with `Touch` 1: IPOC, cycle count, A1–A6, previous A1–A6). `python/rsi_packet_timing.py` analyses read and reply timing of one capture file. Six complete calibration sessions exist: `calibration_20261114_170013_165`, `calibration_20261117_113235_576`, `calibration_20261117_121258_825`, `calibration_20261117_124928_908`, `calibration_20261117_132108_323`, `calibration_20261118_113045_223`; `calibration_20261117_130745_826` has 18 touches. The two oldest use the bare timestamp as identifier (files `rsi_calibration_plan_<ts>.csv`, `rsi_packets_<ts>*.csv`, `rsi_touches_<ts>.csv`); the others use `rsi_plan_<id>.csv`. Only the last one has `calibration_result_<id>.csv`.
