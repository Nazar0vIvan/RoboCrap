# Работа с проектом ISPSoft

Используй `ispsoft.py` рядом с этим файлом. Проверенный формат: ISPSoft 3.19 / AS332T / CP1252, проект и POU без защиты. Поддержаны Programs/FB на ST/LD, SFC Programs со ST Actions/Transitions, STRUCT/ENUM. Достаточно `python.exe`, без зависимостей. Bridge не является компилятором.

## Рабочий цикл

1. Найди актуальную отдельную папку PLC-проекта `<native>` с одним `.isp` в корне и всеми сопутствующими файлами/подкаталогами. ISPSoft должен сохранить и закрыть проект. Не передавай корень большого проекта; не изменяй native.
2. Извлеки исходники: `python.exe "<bridge>/ispsoft.py" export "<native>" "<workspace>"`. Для задачи на анализ достаточно экспорта и чтения; не собирай проект без правок.
3. Измени только нужные файлы в `<workspace>/src/`. Не меняй конвертер, `state.json`, неизвестные поля. Проверяй зависимости в объёме задачи.
4. Проверь: `python.exe "<bridge>/ispsoft.py" status "<native>" "<workspace>"`. `native_changed` должен быть `false`, список `text` — соответствовать задаче. При конфликте/`REFUSED` не обходи защиту; сохрани правки и согласуй с новой базой.
5. Собери: `python.exe "<bridge>/ispsoft.py" build "<native>" "<workspace>" "<output>"`. Каталоги должны быть раздельными, не вложенными; workspace для export и output для build — не существовать. Подставляй реальные пути. `build` проверяет структуру, точное повторное извлечение и CRC; копирует сопутствующие файлы, кроме `*.bak`, `*.~bak`, `~$*`. Сверь `changed_text` с задачей; не дублируй встроенные проверки.
6. Сообщи полный путь выходного `.isp`, изменения и ограничения. Пользователь открывает выходную копию в ISPSoft Offline, сверяет затронутые диаграммы, компилирует (`Ctrl+F7`; неиспользуемые изменённые POU — также `Alt+F7`) и сохраняет. Bridge оставляет прежние данные компиляции; не утверждай, что компиляция/исполнение проверены. Не подменяй оригинал без явного согласования, не подключайся к ПЛК и не загружай программу.

## Где редактировать

Пути относительно `<workspace>/src/`:

| Объект | Файлы |
|---|---|
| DUT | `DUT/<name>.st` |
| ST Program / FB | `Programs/<name>/<name>.st` / `FunctionBlocks/<name>/<name>.st` |
| Local Symbols | `LocalSymbols.txt` в папке POU |
| Global Symbols → Main Table | `Sections/GLOBAL_VAR.txt` |
| Tasks | `Sections/TASK.txt` |
| LD | `LD-Networks.txt` в папке POU |
| SFC | `SFC-Nodes.txt`, `Actions/*.st`, `Transitions/*.st` в папке POU |

## Правила изменения структуры

- ST и переменные: используй синтаксис существующих деклараций ISPSoft. `[@@]` — проверенный вариант для обычных новых локальных переменных, включая экземпляры FB. Не копируй чужие адреса; сохраняй явно назначенные и физические адреса, проверяй пересечения диапазонов для новых переменных. Автоматические адреса могут измениться после Compile/Save.
- POU: согласуй `Definition.txt` (`P_Name`, `P_type`: 0 Program, 1 FB; `P_Lang`: 4 ST, 1 LD, 3 SFC), папку, имя файла и маркеры `@@ISP_SECTION:...@@`. Создавай по существующему аналогу. Обнови `Sections/POUOrder.txt` (строки `Programs/<name>` и `FunctionBlocks/<name>`, Programs перед FB), `ProgramFolder.txt` / `FBFolder.txt` в Sections (`ContentType=0/1`, `ContentName`, `ContentPath`; пустой путь — корень; `-1` — папка). Для исполняемой программы — `T_PName=<name>` в нужном блоке `[TASK_S]`…`[TASK_E]` с нужным порядком; для FB — объявление и вызов экземпляра, не Tasks.
- DUT: согласуй имя в `TYPE`, файл и `Sections/DUTOrder.txt` (`имя<TAB>0` STRUCT, `имя<TAB>1` ENUM); учитывай зависимости от размеров/порядка полей и значений ENUM.
- Переименование/удаление: обнови все применимые ссылки с учётом области видимости (ST, декларации, LD/SFC, Tasks, индексы); удали лишние файлы/записи. Не выполняй бездумную глобальную замену. Кэш компиляции и таблицу экземпляров FB вручную не меняй.
- LD/SFC: сохраняй связи и порядок узлов, используй проверенные образцы ниже и существующие POU. Не угадывай непроверенные конструкции. HWCONFIG и системные/аппаратные секции не изменяй.
- UTF-8, LF; исходный формат CP1252, кириллица не поддерживается, не транслитерируй автоматически. Сохраняй окончания файлов как у аналога (ST, Actions/Transitions и непустые структурные секции — с LF; исследованные DUT — без конечного LF). Имена объектов: ASCII `[A-Za-z_][A-Za-z0-9_]*`.

## Повторная правка / синхронизация

После Compile/Save/закрытия в ISPSoft используй весь актуальный нативный комплект: IDE обновляет адреса, кэш и сопутствующие `.ini`, `.inivals`, `.pnt` и др. Сделай новый export; не собирай из старого workspace. Для отслеживания двусторонних правок сразу после build экспортируй выходную копию в чистый workspace, затем после работы в ISPSoft:
`python.exe "<bridge>/ispsoft.py" refresh "<output>" "<clean-workspace>" "<new-workspace>"`.
Refresh отказывает при текстовых правках в базе, не выполняет слияние. При конфликте сохрани обе версии и согласуй вручную. Не проводи проверки, не относящиеся к заданию.

## Справка только для правок LD/SFC

**LD.** В `LD-Networks.txt` каждая сеть имеет `<NETWORK_START>`…`<NETWORK_END>` и уникальный `NET_ID` в данном POU. Копируй оболочку и свойства сети из существующего аналога; входные узлы находятся в `<ROOTLINK_START>`…`<ROOTLINK_END>`, выходные — в `<OUTLINK_START>`…`<OUTLINK_END>`. Узел контакта/катушки: `[LD_NODE]`, `TYPE=...`, `DEV_NAME=...`, `[END_LD_NODE]` (каждое поле на отдельной строке). Проверены TYPE=1 (NO), 2 (NC), 4 (спадающий фронт, **не NC**), 13 (обычная катушка). Последовательные контакты записываются подряд. Для двух параллельных контактов `A OR NOT B` проверена такая входная секция:

```text
<ROOTLINK_START>
[LD_NODE]
TYPE=1
DEV_NAME=A
[END_LD_NODE]
[LD_NODE]
TYPE=2
DEV_NAME=B
[END_LD_NODE]
[LD_NODE]
TYPE=6
LNK_C=2
LNK_L=1
[END_LD_NODE]
<ROOTLINK_END>
```

**SFC.** Actions и Transitions разделяют `LocalSymbols.txt` родительского POU. Для добавления ST Action в `<ACT_LIST>` файла `Definition.txt` проверен формат (имя и P/U-адреса ниже — образец, не готовые значения):

```text
<ACT>
ACT_LANG=4
ACT_NAME=MyAction
ACT_DISABLED_RESET_FUNCTION=FALSE
ACT_P_DEV=P15
ACT_A_DEV=U216
<ACTDATA>
<BOOKMARK_MAP>
</BOOKMARK_MAP>
<IL_ST_CODE>
@@ISP_SECTION:Actions/MyAction.st@@
</IL_ST_CODE>
</ACTDATA>
</ACT>
```

Создай соответствующий `Actions/MyAction.st`; в `SFC-Nodes.txt` внутри выбранного `[SFC_NODE]` (до `[END_SFC_NODE]`) добавь привязку:

```text
[SFC_NODE_ACT_LIST]
[NODE_ACT]
QUALIFIER=N
ACTNAME=MyAction
TIME=
[END_NODE_ACT]
[END_SFC_NODE_ACT_LIST]
```

Для нового перехода копируй существующую запись `<TRANS>` в `<TRANS_LIST>` с `TRANS_LANG=4`, `TRANS_NAME`, `ACT_P_DEV`, `ACT_A_DEV`, `<TRANSDATA>` и маркером `Transitions/<name>.st`; код присваивает BOOL имени перехода. Для простой двухшаговой петли `Idle → Start → Work → Return → Idle` проверен обратный порядок записей `[SFC_NODE]`…`[END_SFC_NODE]`:

| TYPE | SYMB | TRNA | Доп. поля |
|---|---|---|---|
| 7 | Idle | пусто | jump |
| 1 | U-адрес Return | Return | — |
| 2 | Work | пусто | список Actions при необходимости |
| 1 | U-адрес Start | Start | — |
| 0 | Idle | пусто | `INIT=1` после TYPE |

Пустые поля записывай как `SYMB=`/`TRNA=`; `jump`, «U-адрес» и «—» — пояснения, не поля формата. Шаги объявляй типом STEP; согласуй `P_SFCDev.*`, `P_INIT_StepDev.*`, STEP-адреса, `ACT_P_DEV`/`ACT_A_DEV` и ссылки на U-адреса переходов. Для новых объектов не копируй занятые P/U-адреса: проверены согласованные предварительные непересекающиеся адреса с последующим переназначением в ISPSoft. Если нельзя обосновать свободные диапазоны или нужную сериализацию, запроси нативный эталон из IDE. Проверены простая петля, ST Actions с N и их привязка к шагам; произвольные графы, другие языки внутри SFC и исполнение на реальном ПЛК не верифицированы.
